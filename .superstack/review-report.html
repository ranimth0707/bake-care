Arisan protocol review

Outcome: B. The repeated-winner correctness bug is fixed and the fund-transfer paths retain signer, PDA, ownership, and checked-arithmetic protections. The new reserve guard prevents a defaulting member from making another member's payout short.

Resolved high-severity correctness issue

The old draw used seed % member_count, so a prior winner could be selected again. A compact on-chain winner bitmap now removes prior recipients from the candidate population before selection. Claim updates the bitmap atomically.

Security checks

  • Creator has no instruction that transfers the pot to an arbitrary destination.
  • Pot and bond PDAs are re-derived from the circle and signed only by program seeds.
  • Only the selected, signing wallet can claim, and its Member account is PDA-, wallet-, seat-, settlement-, activity-, and winner-checked.
  • Legacy roster migration verifies Anchor ownership/discriminators, circle identity, seat bounds, complete coverage, and winner counts.
  • A new CircleSafety PDA proves per-member reserve coverage and group bond coverage before any draw; an incomplete reserve locks the round.
  • Value arithmetic uses checked operations on the draw/claim path.

Open risks

  • Economic capital requirement: protection now requires each member to lock the full remaining reserve up front. This is conservative and makes the UX less accessible, but it is the cost of guaranteeing a whole pot.
  • Upgrade trust: the program remains upgradeable by a single authority. Move it to a 2-of-3 multisig before material TVL; do not use 3-of-3 without a recovery plan.
  • Dependencies: npm reports transitively inherited advisories in Anchor/Web3 dependencies with no upstream fix available.

Verification

3 Rust bitmap tests, 49 frontend/relayer tests, TypeScript production build, live program upgrade verification, and targeted reserve-policy regressions. The full mainnet arisan script should be rerun after this safety upgrade.
